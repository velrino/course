# Retrieve, Space, and Interleave

## Learning objectives

By the end of this lesson, you will be able to:

- use retrieval practice instead of recognition as the main review activity;
- schedule reviews across time without building a complicated system;
- interleave related problem types when discrimination matters; and
- give yourself feedback without turning review into copying.

## Retrieval changes memory

Retrieval practice means attempting to produce an answer from memory. It is not the same as reading a flashcard front and immediately revealing the back. The attempt must happen before feedback.

In experiments using educational prose, repeated studying helped on a test minutes later, but prior testing produced better retention after delays. The practical lesson is not "never reread." It is: use the source to learn and correct, then practice the act you will need later: retrieving and applying.

Good retrieval prompts require production:

- "Draw the HTTP exchange and label each part."
- "Explain image versus container without using the word Docker."
- "Given this scenario, choose tool, resource, or prompt and justify it."
- "Write the command, predict its output, then run it."

Weak prompts invite recognition:

- "Does this explanation look familiar?"
- "Read these notes again."
- "Highlight the important sentence."

## Space reviews across time

Spacing means distributing practice rather than compressing it into one session. There is no universally perfect interval. A simple starting schedule is:

- first retrieval: at the end of the lesson;
- second: the next day;
- third: about three days later;
- fourth: about one week later;
- then extend the interval when recall is accurate and usable.

Shorten the next interval after a failed retrieval, but always inspect the correction before trying again. The goal is effortful success, not repeated guessing.

## Interleave decisions, not random facts

Blocked practice repeats one type: five `GET` examples, then five `POST` examples. Interleaved practice mixes related types so you must first identify what kind of problem you face. This is useful when real work demands discrimination.

For example, mix these prompts:

1. retrieve a record without changing state;
2. replace the client-provided state at a known URI;
3. submit an event that creates a server-named item;
4. remove a record; and
5. update only selected fields.

Now the learner must choose a method before applying it. Do not interleave unrelated beginner tasks so aggressively that working memory is overwhelmed. Learn the basic form, then mix close alternatives.

## Use feedback as correction data

After every attempt, mark:

- **correct and supported;**
- **correct but poorly explained;**
- **missing;**
- **incorrect;** or
- **lucky guess.**

Convert only missing, incorrect, and fragile parts into the next retrieval prompt. This keeps practice targeted.

## Free local practice

Create ten retrieval prompts from the first two lessons. Put the questions in one text file and answers in another so they cannot be seen accidentally.

1. Answer all ten without sources.
2. Score each with the five labels above.
3. Schedule only weak items for tomorrow.
4. Add two application questions that change the examples.
5. In three days, mix these questions with five questions from your current technical module.

A calendar, paper index cards, or a text file is sufficient. A spaced-repetition application is optional, not a prerequisite.

## Completion criteria

- [ ] You attempted retrieval before viewing answers.
- [ ] At least half your prompts require explanation, generation, or a decision.
- [ ] You recorded error type rather than only a numeric score.
- [ ] You scheduled at least two future reviews on different days.
